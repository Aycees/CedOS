Ced OS — Build Planning Document

DRAFT · FOR STACK-SELECTION DISCUSSION · AUG 2026

Personal life-management platform: calendar, journal, notes, finance/budget tracking, a credentials vault, habit tracking, and itinerary planning, unified in one dashboard ("Today" view) with day/night themes.

This document scopes what it takes to turn the current frontend mockup into a real, secure, well-architected product. It's meant as input to a stack-selection conversation, not a final spec — stack is intentionally left open below.

01What exists today

A single-page, client-only mockup (mock/in-memory data, no backend, no auth, no persistence beyond the session). Modules visible in the UI:

ModuleData it will hold
Today (dashboard)Aggregated view of the below — no independent data
CalendarEvents across categories (School, Personal, Money, Health, Travel)

NotesFree-text notes
HabitsHabit definitions + daily completion logs

The Vault module is the one that changes the entire security posture of the project — a credentials store has fundamentally different requirements than a journal or a habit tracker. Treat it as a password-manager-grade subsystem, not "just another app," from day one.

02Data classification

Sensitivity drives the security requirements, so classify first:

TIER 0 — SECRETS

Vault credentials (passwords, PINs, account numbers, security answers). Compromise = direct account takeover elsewhere. Requires the strongest protection: client-side encryption, ideally zero-knowledge (server never sees plaintext).

TIER 1 — SENSITIVE PERSONAL

Journal entries, finances (balances, transactions), itineraries (reveals travel dates → physical security risk, e.g. "when is the house empty"). Requires encryption at rest, strict access control, no third-party analytics/logging of content.

TIER 2 — PERSONAL, LOWER-STAKES

Calendar events, notes, habits. Still private, still needs auth + standard protections, but exposure is less catastrophic than Tier 0/1.

Design the data layer so Tier 0 data is architecturally separated (different encryption keys, ideally a different table/service) from Tier 1/2 — never let a single bug in the notes feature leak vault contents.

03Architecture (stack-agnostic)

Rather than lock a stack here, these are the decisions that matter regardless of what you pick, since the stack conversation is happening elsewhere:

Client / server split

A full client-side app (e.g. local-first with IndexedDB only) avoids server-side breach risk but loses multi-device sync and makes recovery-on-device-loss hard. A thin client + backend API is the more standard, recoverable choice, and is assumed below.

Multi-tenancy from day one

Even if it's single-user today: every table gets a user_id/owner_id foreign key and every query is scoped by it — retrofitting this later is how horizontal privilege-escalation bugs get born.

Database

A relational DB (Postgres) fits this data well — structured entities (transactions, events, habits) with relations (budgets → transactions, trips → itinerary items). Use row-level security if the DB supports it (Postgres RLS) as defense-in-depth under app-layer authorization, not instead of it.

API style

REST or a typed RPC layer (tRPC, etc.) — either is fine; prioritize whichever gives you end-to-end types with your frontend choice, since this is a wide, entity-heavy app.

Hosting

Managed platform (Vercel / Railway / Fly / Render + managed Postgres) over self-managed servers for a project this size — less infrastructure surface to secure and patch.

04Security

Authentication

  • Use a managed auth provider (Auth.js/NextAuth, Clerk, Supabase Auth, WorkOS) rather than hand-rolled auth. Password hashing, session tokens, and email verification are easy to get subtly wrong and hard to audit yourself.
  • Require MFA (TOTP at minimum) — strongly recommended given the Vault module; consider making MFA mandatory specifically to unlock Vault, even if the rest of the app allows password-only login.
  • Session tokens: short-lived access token + refresh token, httpOnly + Secure + SameSite=Strict cookies. Never store tokens in localStorage (XSS-exfiltrable).
  • Rate-limit login and password-reset endpoints (e.g. 5 attempts / 15 min / IP+account) to blunt credential stuffing.

Vault (credentials) — its own threat model

  • Zero-knowledge encryption: derive an encryption key client-side from the user's master password (Argon2id or PBKDF2, high iteration count), encrypt/decrypt vault items in the browser, store only ciphertext server-side. The server should never be able to decrypt vault contents, even under subpoena or breach.
  • This means: password reset for the master vault password must be handled differently from account password reset — a lost master password should mean lost vault access, with an explicit recovery-key mechanism the user saves themselves (the same trade-off 1Password/Bitwarden make).
  • Auto-lock the vault UI after inactivity (e.g. 5 min) independent of the app session.
  • Never log vault plaintext, even in debug/dev logs. Add explicit tests asserting vault fields never appear in server logs or error-tracking payloads (Sentry, etc.).

Data protection (Tier 1/2)

  • Encryption at rest for the whole database (most managed Postgres providers do this by default — verify it's on).
  • Consider field-level encryption for finance data (account numbers, balances) and journal text, using a server-held key (KMS-managed) — a lighter bar than Vault's zero-knowledge requirement, but still real protection.
  • TLS everywhere (default on any managed host — confirm HSTS is enabled).
  • Backups encrypted, access-logged, and tested for restore — a backup is a second copy of Tier 0/1 data and needs the same scrutiny as the primary store.

API hardening

  • AuthZ check on every mutating and every reading endpoint — verify resource.owner_id === session.user.id server-side, not just in the client. This is the single most common real-world bug class here (IDOR — user A fetching user B's transaction by guessing/incrementing an ID).
  • Input validation on every endpoint with a schema library (Zod, etc.), shared between client and server where possible.
  • Parameterized queries / an ORM (Prisma, Drizzle) — never string-concatenated SQL.
  • CSRF protection for any cookie-authenticated mutation.
  • Standard security headers: CSP, X-Content-Type-Options, X-Frame-Options/frame-ancestors, Referrer-Policy.
  • Sensible per-user and per-IP rate limiting on all endpoints, not just auth.
  • Dependency scanning (npm audit/Dependabot/Snyk) in CI — keep the many small packages (date libs, chart libs) patched.

Secrets management (yours, not the user's)

  • API keys, DB credentials, encryption keys live in environment variables / a secrets manager (Doppler, host's built-in secrets) — never committed, never in client bundles.
  • Rotate keys on any suspected exposure; document the rotation procedure now while it's cheap to write down.

05Code architecture & cleanliness

  • Module boundaries mirror the app's domains: calendar/, journal/, notes/, habits/, money/, vault/, itineraries/, each with its own data access, validation, and UI, rather than one flat components/ and api/ dump. Vault especially should be isolable — easier to audit, easier to reason about what can touch encrypted data.
  • Shared kernel: auth/session, the design system (theme tokens, typography, the paper/dark themes already in the mockup), and generic UI primitives as a shared layer other modules import, not copy-paste.

Testing

  • Unit tests for anything with logic: budget calculations, habit streak/rate math, recurrence rules for calendar events, encryption/decryption round-trips for Vault.
  • Integration tests for API authorization — the IDOR class of bug above is exactly what these should catch ("user B cannot read user A's data" as an explicit test per resource type).
  • E2E smoke tests (Playwright) for critical paths: login, add/view a vault item, add a transaction, complete a habit.

CI & environments

  • Lint + typecheck + test + dependency audit on every PR, before merge. Cheap to set up now, expensive to retrofit once the app has real users.
  • ESLint + Prettier (or the stack's equivalent) enforced in CI, not just locally.
  • Separate dev / staging / prod, with staging using synthetic (never real user) data.
  • Structured error tracking (Sentry) with PII/Vault-field scrubbing configured explicitly — don't rely on remembering not to log sensitive fields; scrub at the logging layer.

06Accessibility

The mockup already uses a legible serif/mono pairing and two themes — good starting point. To carry that through:

  • Contrast: verify both Paper and Dark themes hit WCAG AA (4.5:1 body text, 3:1 large text/UI) — check the muted-text colors specifically; muted/secondary text is where contrast usually fails first.
  • Keyboard navigation: full app usable without a mouse — nav drawer, calendar grid, habit checkboxes, vault item reveal/copy, all reachable and operable via keyboard, with visible focus states (not just outline:none as currently set on inputs — replace with a visible custom focus ring).
  • Screen readers: semantic HTML and ARIA labels for icon-only buttons (theme toggle, hamburger, settings gear) — several currently render as bare SVGs/glyphs with no aria-label in the mockup.
  • Forms: every input has an associated <label> (not just placeholder text), and errors are announced (aria-live), especially relevant for Vault (password fields) and Money (amount entry).
  • Reduced motion: respect prefers-reduced-motion for any transitions/animations added later.
  • Sensitive-content specific: a screen reader announcing a vault password character-by-character in a public space is itself a leak — make "reveal password" an explicit user action, never on-focus auto-announce.

07Open decisions (for the stack conversation)

  • Framework (Next.js / Remix / SvelteKit / etc.) and whether SSR matters here (mostly private, logged-in views — SSR benefit is smaller than for a public marketing site).
  • Managed auth provider vs. custom (recommendation above: managed).
  • Local-first/offline support — worth having itineraries/notes available offline? Affects sync architecture significantly if yes.
  • Mobile: responsive web only, or a native/PWA wrapper later? Affects how "install as app" and offline are handled.
  • Whether Vault is built in-house per section 4, or whether integrating an existing password-manager API/SDK is preferable to owning that liability yourself.

08Suggested next steps

  1. Finalize stack (separate conversation).
  2. Stand up auth + multi-tenant DB schema first, before porting any UI module — every feature after this point should be built "user-scoped" from the start.
  3. Build Vault's encryption layer second, in isolation, with tests, before wiring it to UI — it's the highest-risk piece and the one hardest to retrofit.
  4. Port remaining modules (Calendar, Journal, Notes, Habits, Money, Itineraries) onto the real backend.
  5. Add CI (lint/type/test/audit) before the first module ships, not after.
  6. Accessibility pass once core flows are real (contrast, keyboard, ARIA) — cheaper to fix while components are still being written than after the fact.
